# ATLAS 需求规范化（v3.3）

把用户的自然语言，转成**可逐条勾选确认**的规范要求，最后输出一份 JSON 交给下一个页面。

- 三个问题：商品类型 → 硬性约束 → 零件拆解
- 所有 AI 输出走**预设函数**（function calling + 严格 JSON Schema 校验）
- 每轮结果在弹窗中逐条列出，**点击卡片切换选中，边框高亮表示生效**
- 弹窗底部固定三个动作：拒绝全部重来 / 保留已选重来 / 保留已选继续
- 完成后 JSON 写入 `window.__REQUIREMENT_PAYLOAD__`、`localStorage`，点「进入下一阶段」交接给 `next.html`

零依赖：Node 原生 `http` + 原生前端，不需要 `npm install`。

## 启动

```bash
cd atlas/pages
node server.mjs
# 打开 http://127.0.0.1:43125
```

默认端口 `43125`，可用 `PORT` / `HOST` 覆盖。

## 公网访问（Cloudflare Tunnel，可选）

不需要把代码上传到 Cloudflare —— 用隧道把本机服务映射成一个 https 地址，`data/` 仍然留在这台电脑：

```powershell
# 窗口 1：先跑服务
node server.mjs

# 窗口 2：开隧道
.\start-tunnel.cmd
# 等价于 tools\cloudflared.exe tunnel --url http://127.0.0.1:43125 --no-autoupdate
```

终端会打印一个 `https://<随机名>.trycloudflare.com`，手机 / 别的电脑直接打开即可。

注意：

- 这是 cloudflared 的 **quick tunnel**：地址每次启动都会变，Cloudflare 不保证可用性；要固定域名需要账号 + 命名隧道（`cloudflared tunnel create` + DNS 绑定）
- 服务必须保持运行；电脑休眠、断网或关掉隧道窗口，链接立即失效
- **目前没有访问密码**：拿到链接的人可以新建身份码、读写产品、消耗你的 AI 额度，只发给自己人
- 走隧道时所有人共享同一个出口 IP，限流按 `CF-Connecting-IP` 区分（已处理），仍建议别把链接公开

## 身份码与产品保存

打开页面先填**身份码**（2–32 位字母 / 数字 / 下划线 / 短横线 / 中文，统一小写）：

- 身份码对应的文件夹**已存在** → 提示「是否登录」
- **不存在** → 提示「是否创建」，创建时建目录并写入 `identity.json`

每个身份码固定对应本地一个文件夹（默认在项目根目录）：

```
data/
  alice/
    identity.json
    untitled1.json
    云台方案A.json
```

三个问题都确认后进入**命名环节**：默认名从 `untitled1` 开始按已有文件顺延（`untitled2`、`untitled3`…），保存后 JSON 写入该身份码目录。

右上角「我的」：

- 显示当前身份码、本地文件夹、已保存数量
- 列出历史产品（名称 / 保存时间 / 零件数 / 层级），点一行即把该 JSON 读回页面，直接恢复成完成状态
- 底部「切换身份」退出当前身份，回到身份码输入

说明：

- **刷新页面不清缓存**：进度、身份码、登录态都会保留（sessionStorage 存活标记 + 服务端会话），刷新后直接回到原来的位置
- **关闭标签页 / 窗口后重新打开才清空**：缓存（localStorage 里本应用的所有键）与登录态一起清掉，回到身份码入口；已保存到文件夹里的产品不受影响
- **「退出登录」仍然清空缓存**并回到身份码入口（主动退出，与关闭同义）
- 同一浏览器开多个标签页时互相识别，不会因为开新标签页把正在用的进度清掉
- 保存接口需要登录态（内存 Session + HttpOnly Cookie），重启服务后同样需要重新输入一次身份码
- 服务端只暴露相对于项目的路径，Key 与文件系统绝对路径不会下发给前端
- 存放位置可用 `ATLAS_DATA_DIR` 覆盖，例如 `ATLAS_DATA_DIR=D:\atlas-data node server.mjs`；目录结构说明见 `data/README.txt`

## 接入真实 AI（只改一个文件）

编辑整合包根目录的 **`../ai-config.env`**（`atlas/ai-config.env`），填好 Key 和地址并保存：

```ini
AI_API_KEY=sk-...
AI_BASE_URL=https://api.deepseek.com
AI_MODEL=deepseek-chat
```

**保存后刷新页面即生效，不需要重启服务。** 常用端点：

| 服务 | `AI_BASE_URL` | `AI_MODEL` |
| --- | --- | --- |
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat` / `deepseek-reasoner` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` / `gpt-4o` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 本地 vLLM / Ollama | `http://127.0.0.1:8000/v1` | 你部署的模型名 |

- 键名大小写不敏感，`api_key` / `url` / `model` 也能识别；支持引号、`:` 分隔与 `#` 注释。
- 取值优先级：`../ai-config.env`（根目录，唯一生效位置）> `pages/ai-config.env`、`pages/.env`（旧位置，兼容用）> 进程环境变量 > 内置默认值。
- 清空 `AI_API_KEY` 即回到 **mock 模式**：本地规则模拟同样的双输出，全流程可演示。
- 端点写错时右上角徽标显示「配置错误 · 检查 ai-config.env」，接口返回 503 并说明原因，不会静默降级。
- API Key 只在服务端读取，`/api/config` 不会下发 Key。

右上角徽标随之切换：

| 状态 | 徽标 |
| --- | --- |
| 联网 | `DeepSeek · deepseek-chat`（来源 · 模型） |
| 本地 | `MOCK · 本地预设函数` |
| 配置有误 | `配置错误 · 检查 ai-config.env` |

> 旧版把配置放在 `pages/ai-config.env` 或 `pages/.env`，这两个位置仍然会被读取，但优先级低于根目录那份；
> 新装的包只认 `atlas/ai-config.env`。后端 `backend/` 也读同一份，改一次两端同时生效。


## 一次请求的双输出

`POST /api/normalize`

```json
{ "questionId": "parts", "text": "拆到零件级…", "context": {...}, "carryOver": [...] }
```

响应同时包含：

| 字段 | 含义 |
| --- | --- |
| `reply` | AI 面向用户的自然语言，前端**原样展示**，不二次改写 |
| `result` | 预设函数返回并校验后的结构化 JSON |
| `functionName` | 本次调用的预设函数 |
| `warnings` | 归一化过程中的修正提示（如重复编号被改名） |

预设函数：

| 问题 | 函数 | 输出 |
| --- | --- | --- |
| Q1 商品类型 | `submit_product_type` | 1 个主类型 + 最多 2 个备选（单选） |
| Q2 硬性约束 | `submit_hard_constraints` | 完整约束集合（多选，默认不选） |
| Q3 零件拆解 | `submit_parts` | 从表1 预设里选模块/零件（L1 固定、L2/L3 二选一、L3 全覆盖） |

真实模型若只返回工具调用、没有自然语言，会再发一次"只写回复"的请求补齐；仍然失败则整次请求报错，不会展示半成品。

## 表1 查看页

页面右下角的「表1 v2.0.0 · 7 个模块 / 28 个零件 ↗」是超链接，点开 `table1.html`：

- 直接渲染 `GET /api/table1`（`presets/table1.json` 原文），不复制数据，改表后刷新即同步；
- 列出商品类型（目前只有 `h3` 手持云台）、L2 模块与 L3 零件（含编码、用量、说明）、拆解层级（L1–L3）、约束维度、预设函数，以及文件开头的「格式与编码」规则；
- 右上角「原始 JSON ↗」可看接口原文。

### 表1 v2 的编码与选择规则

| 层 | 编码 | 例子 | 含义 |
| --- | --- | --- | --- |
| L1 | 商品类型 id | `h3` | 整机，永远包含、不可取消，且**不覆盖**下级 |
| L2 | `<L1>-<模块缩写>` | `h3-cam` | 模块，选中即代表整块采购，其下 4 个零件视为已覆盖并从清单隐藏 |
| L3 | `<L2>-<两位序号>` | `h3-cam-01` | 零件，只在所属模块被取消勾选时展开，并锁定为已选 |

- AI 只能返回表1 里存在的 code，自造编码会被丢弃并写入 `warnings`；
- 同一模块内 L2 与 L3 二选一，不允许上下重合（同时出现时保留零件）；
- 每个 L3 必须被覆盖：要么选它的 L2，要么直接选该 L3；只选部分零件会自动补齐其余零件；
- L4（材料 / 工艺级）自 v2.0.0 起暂时停用，`bomLevel` 只接受 `L1 / L2 / L3`。

## 选择与重来语义

- **Q1**：单选，默认选中 AI 主类型。
- **Q2**：默认全部不选，逐条勾选才生效。
- **Q3**：L1 固定选中；默认 7 个模块全部整选。取消某个模块会立刻展开它的 4 个 L3 并锁定为已选，重新勾选模块即收回；L2/L3 不允许同时选中，L3 不允许缺项。
- **保留已选，重新提问**：已选条目全部保留；下次弹窗中即使 AI 没有重新返回它们，也会以虚线卡片重新出现并保持选中。
- **拒绝全部，重新提问**：清空本题的 AI 结果、已选条目和输入框。
- **保留已选，继续**：至少选中 1 条才能继续；本题打上已完成标记，进入下一问。

## 输出 JSON

完成三个问题后，摘要卡上会直接提供「进入下一阶段」：

```js
window.__REQUIREMENT_PAYLOAD__ // 当前页完整载荷
// 或
JSON.parse(localStorage.getItem("atlas.requirement-intake.v2.<身份码>")).payload
```

结构（节选）：

```jsonc
{
  "schemaVersion": "atlas.requirement-baseline/v2",
  "status": "complete",
  "result": {
    "productType": { "presetId": "h3", "name": "h3 手持云台" },
    "constraints": [{ "dimension": "weight", "operator": "<=", "value": "800", "unit": "g" }],
    "parts": [
      { "code": "h3", "name": "h3 手持云台", "level": "L1", "qty": 1 },
      { "code": "h3-cam-01", "name": "相机模组", "level": "L3", "qty": 1, "parentCode": "h3-cam" },
      { "code": "h3-pit", "name": "俯仰轴总成", "level": "L2", "qty": 1, "parentCode": "h3" }
    ],
    "bomLevel": "L3",
    "bomLevelName": "零部件级"
  },
  "questions": [{ "id": "product_type", "rounds": 2, "selectedCount": 1 }],
  "handoff": { "target": "next-page" }
}
```

`parts` 里只写用户最终勾选的条目（L1 + 整选模块 + 展开的 L3），不额外展开整选模块的零件；`bomLevel` 取所选条目里的最深层级（有 L3 即 L3，否则 L2）。

### 保存到「我的」

命名保存后，同一份 JSON 写入 `data/<身份码>/<产品名>.json`，并追加四个字段：

```jsonc
{
  "projectName": "云台方案A",
  "savedAt": "2026-10-30T14:28:48.000Z",
  "savedBy": "alice",
  "storage": { "folder": "alice", "file": "云台方案A.json" }
}
```

文件名里的 `\ / : * ? " < > |` 会替换成 `_`，重名自动加 `-2` / `-3` 后缀；内容仍是完整的 handoff 载荷。

## 进入下一阶段（交接给下一页面）

摘要卡主按钮「进入下一阶段」不再下载文件，而是把整份 JSON 交给下一页面：

1. 浏览器 `POST /api/handoff`（`{ name, payload }`）；
2. 服务端写入 `data/.handoff/<令牌>.json`，返回 `next.html?handoff=<令牌>`；
3. 浏览器跳到该地址；
4. `next.html` 用 `GET /api/handoff/<令牌>` 读回同一份 JSON，挂到 `window.__STAGE2_PAYLOAD__`，进入第二页的方案配置。

约束：

- 交接内容只有生成它的身份码（同一个登录 Cookie）能读回，链接被转发也读不到；
- 令牌是 32 位随机十六进制，12 小时后过期，过期后提示回到需求页重进；
- 第一页顶部按钮已改为「进入下一阶段」，JSON 下载/复制移到了第二页的「需求 JSON」弹窗；
- 第二页直接打开会提示缺少令牌；本地预览用 `next.html?demo=1`。

## 第二页：方案配置与对比

第二页在 `next.html`，接收第一页的 JSON 后进入：

- **左栏 · 用户自配器**：按表1 的 7 个模块 / 28 个零件类型列出；点零件类型展开 **10 个型号**（基础四款：标准 / 轻量 / 增强 / 旗舰，+ 两个厂家各 3 款），点「加入」写入当前用户方案。每张卡片直接显示 `单价 · 重量 · 性能分`。
- **两个入口**：
  - **从系统推荐开始自配**：复制**当前的系统推荐**（不是固定的 CSV 基线，而是用极速引擎按当前权重搜出来的组合）成一个新的「用户自配 1」，可逐项替换；
  - **从零开始自配**：创建一个全空的「用户自配 N」，必须填满 28 个零件类型。
  - 每点一次，新列追加到对比矩阵最右侧；可删除、可清空。
- **中栏 · 对比矩阵**：列 = 系统推荐（只读）+ 用户自配 1/2/3…；行 = 模块 / 零件类型；格子 = 该方案选中的零件名，悬停显示单价、重量、交期等核心参数。左侧零件列约占表宽 1/4（140–240px 自适应），模块名左对齐；用户方案删除中间一列后按当前顺序重新编号。
- **标题 · 硬约束**：标题位置直接列出第一页的硬约束，每条都可悬停 / 键盘聚焦查看完整条件、系统推荐实际值和是否达标；无法自动计算的维度标为「需人工确认」。
- **右栏 · 零件详情**：顶部是该零件**类别的示意图**（28 张，同类 10 个型号共用一张，`public/data/parts/<类型代码>.svg`），下面是当前型号的厂家 / 型号 / 核心参数 / 性能分 / 单价 / 重量 / 交期 / 风险分、责任人与说明。
- **对比门槛**：至少一个用户方案，且所有用户方案的 28 个零件类型都填满，`开始对比` 才可用；对比后显示每个方案的成本 / 重量 / 综合性能 / 风险分（含交期）/ 最长交期、硬条件满足情况，并高亮差异零件。
- **硬条件校验**：从第一页的 `result.constraints` 读取，目前自动校验 **重量（weight）/ 成本（budget）/ 交期（lead_time）**；其他维度（如 IP54、认证）会在对比结果中标注「需人工确认」。不满足硬约束的方案在列名旁显示 `!`，只差软约束的显示 `~`，悬停都能看到具体条件。约束的软硬取自第一页的 `priority` 字段：`must` = 硬约束、`should` = 软约束（软约束在硬约束区用虚线下划线 + `软` 小标签标出）。
- **方案评分**：对比结果下方是「自定义加权评分」——成本 / 重量 / 性能 / 风险（含交期）/ 约束五个维度，可拖权重、切场景预设、重置，实时给出排名与首选方案；口径见下面「方案评分（加权）」。
- **交付排期**（第二页第二个页签）：见下面「交付排期：甘特图 + 流程图」。

零件库在 `public/data/h3-parts.json`（完整路径 `atlas/pages/public/data/h3-parts.json`；28 个零件类型 × 10 个型号 = **280 条**）：

- 28 个零件类型 × 10 个型号；`tierKey: "std"` 的标准件是系统推荐的起点之一（`baselineVariantId` 指向它）；
- 10 个型号分两组，但**字段和展示格式完全一致**：
  - 基础四款：`std` 标准 / `lite` 轻量 / `plus` 增强 / `pro` 旗舰，型号形如 `H3CAM01-S / -L / -P / -X`，挂在「基线供应商」名下；
  - 厂家款：`tierKey: "market"`，两个厂家各 3 款，型号形如 `H3CAM01-201 / -301`，带 `links`（1 条 primary + 2 条 secondary 的模拟平台链接）；
- 每个型号字段：`manufacturer / model / price / weight / leadTime / risk / material / spec / owner / description / source`，外加：
  - `coreParams`：3 个核心参数（`{label, value, score}`），如相机 = 分辨率 / 帧率 / 低照度；
  - `performance`：0–100 性能分，由 `coreParams` 按绝对区间归一化后加权得到（权重写在 `part.performanceBasis` 里）；
- 性能分口径：每个参数有工程上合理的取值区间与方向（越大越好 / 越小越好），`score = 归一化位置 × 100`，性能分 = Σ(参数分 × 权重)。与对手无关、只看型号自己的规格；
- 文件开头的 `$comment` 就是格式说明；改这个文件不需要改前端，新增类型时 `code` 必须与 `presets/table1.json` 的 L3 编码一致；
- 页面结构（模块、零件名、数量）仍以 `GET /api/table1` 为准，零件库只提供型号与参数；
- 重新生成演示库：`node atlas/scripts/gen-parts.mjs --write`（确定性生成，先读现有基础四款的价 / 重量 / 交期，再补齐厂家款与性能分）。

### 系统推荐（极速引擎：多起点爬山）

「系统推荐」这一列不是固定的 CSV 基线，而是按**当前评分权重**在零件库里搜出来的组合。界面上把它叫「极速引擎」，算法是**多起点爬山**：

1. **五个起点**，每个起点先把 28 个零件整套铺好：
   - 全标准件（每类取 `tierKey: "std"`）、全最低价、全最轻、全最高性能、全最低风险（风险等级 + 交期档位排序）；
2. **每一路各自爬山**：每轮扫遍「只换一件」的所有候选（28 类 × 其余 9 个型号 = 252 次试算），执行涨分最多的那一步，再重扫；
3. **直到这一路没有单件替换还能涨 ≥ 0.05 分**——此时是这一路的 1-邻域局部最优；
4. **五路跑完取分数最高的那一路**作为系统推荐；起点重复的（例如某类全最便宜恰好就是标准件）会跳过，不重复试算；
5. 每一步都留明细（哪个零件、从什么换到什么、涨了几分），悬停评分区顶部的「推荐引擎」条可以看到**每一路的起止分**和**获胜那一路的全部置换**。

**为什么是多起点**：爬山只能保证局部最优，单个起点会卡在离起点最近的那个坑里。实测（`__STAGE2_SOLVER_CHECK__(3)`，裁剪到 3 类 1,000 种组合，能精确穷举）：单起点标准件只拿到 75.9，五起点拿到 84.3，而精确枚举的最优解就是 84.3——多起点在这一档把「差 8.4 分」补平了。真实零件库 1.0×10²⁸ 种组合无法穷举，只能说多起点比单起点更接近最优，**不保证全局最优**。

**为什么不穷举**：组合空间 = Π(每个类型的型号数) = 9 × 10²⁷ 量级 ≈ **1.0×10²⁸**，浏览器里跑不完一次完整枚举。`?rec=enum` 保留了一条精确枚举的路径，一旦组合数超过 20 万（`REC_ENUM_LIMIT`）就明确写「已回退极速引擎」，不假装跑过。

**涨分口径**逐级比较：**硬约束违规数 ↓ → 最终得分 ↑ → 封顶前的原始分 ↑ → 软约束违规数 ↓ → 总价 ↓**。先比硬约束，是因为硬约束一破得分就被封在 20，只看最终得分的话所有违规方案都停在同一条平地上，爬山永远走不出违规区；反过来，当所有候选都被封顶（例如约束根本满足不了），就改用封顶前的原始分继续推进——引擎条会写「原始分 +9.0（已封顶）」，而不是假装涨了分。

几个刻意的取舍：

- **只走"真的涨分"的步**：低于 0.05 分（面板显示精度）的边际置换不采纳。全接受的话实测会变成"28 个件换 27 个、总共只多 0.03 分"（最小一步 0.003 分），推荐看起来像被无意义地洗了一遍；
- **"同分但更便宜"不算涨分**，但同分候选之间仍用总价定序（省钱的平手不亏）；
- **权重变了会重算**：拖滑杆时防抖 260ms 重算一次（先把「权重已变，正在重算…」画出去，再跑计算），系统推荐列、评分、对比卡片一起刷新（矩阵滚动位置保留）；已创建的用户方案不跟着变——它们是当时从推荐复制下来的快照；
- **权重全为 0** 时不做优化，保持全标准件并写明原因；
- 一次求解 ≈ **150–300 ms**（5 路、约 2.5–3 万次试算，取决于权重；性能优先这类"小步慢跑"的权重会到 600 ms 左右）；刷新页面会按 `sessionStorage` 里恢复的权重重算，同一权重两次结果完全一致（可复现）。

界面上：矩阵里被换成非标准件的格子前面点一个青色圆点，悬停看「从标准换成了哪一档 + 厂家 / 型号 / 性能分」；评分区顶部的引擎条写明算法、起点数、候选型号数、试算次数、置换次数，以及 `全标准件 60.0 → 系统推荐 80.9`。

> 性能提示：`selectionEval` 走的是「单件指标 + 差值」的增量路径（`variantMetricOf / metricsOf`），约束也预编译成 `constraintPlanOf()`，所以 2～3 万次试算能在几百毫秒内跑完；早期逐次重建整机 Map 的写法要 600 ms 以上。

对应实现：`public/next.js` 的 `candidatePool()` / `standardSelection()` / `REC_STARTS` / `multiStartSelection()` / `hillClimb()` / `enumSelection()` / `optimizeRecommendation()` / `paintEngine()`，样式在 `public/next.css` 的 `.s2-score-engine` 段。

### 方案评分（加权）

对比结果下面的评分区（`#scorePanel`）是参照《ATLAS-三轴云台方案对比与BOM》的「自定义加权评分」做的，口径一致：

| 维度 | 取数 | 方向 | 理想最优 ↔ 最劣（1.5 倍区间） |
| --- | --- | --- | --- |
| 成本 | `totals.price`（BOM 总价） | 越低越好 | ¥1,788 ↔ ¥3,431（可行 ¥2,062–¥3,157） |
| 重量 | `totals.weight`（整机重量） | 越低越好 | 559 ↔ 973 g（可行 628–904 g） |
| 性能 | `metrics.perf` = Σ 型号性能分 × 用量 | 越高越好 | 717 ↔ 3,473 分（可行 1,177–3,013 分） |
| 风险 | 每个型号：风险等级（低 0 / 中 1 / 高 2）占 60% + 交期档位（全库交期三分位，0/1/2）占 40%，归一后对全机取平均 | 越低越好 | 0 ↔ 100（本身就贴着定义域，同样按 1.5 倍拉到 −25～125） |
| 约束 | 硬约束满足率 `(checked - violations) / checked`，没有可校验约束时按满足计 | 越高越好 | −25% ↔ 125%（可行 0–100%） |

标尺由**零件库本身**决定：逐个零件类型取所有型号（基础款 + 厂家款）的最小 / 最大单价×用量、单重×用量、性能分×用量，累加得到成本 / 重量 / 性能区间；风险是归一化指标，定义域就是 0–100。得到可行区间后，**理想最优解与最劣解各向外拉 25%，总长变成可行区间的 1.5 倍**——贴到可行边界的方案拿 83 分左右而不是 100 分，留出"还没到极限"的空间。这层含义只写在代码注释里，界面上不再解释（v3.2 删掉了评分区顶部那段说明）。

这套标尺在一轮对比里是固定的——**评分只看方案自己，不看这一轮有哪几个对手、它们表现多差**。所以删掉一个差方案，或者拉进来一个更差的方案，别的方案分数不会变（这一点是硬要求：不能因为对手不合格就送别人满分）。

- 维度得分 = 该方案取值在（拉长后的）标尺中的线性位置（成本/重量/风险反向，性能/约束正向），超出标尺的范围按 0 或 100 截断；
- 综合得分 = **√(Σ 维度得分 × 归一化权重) × 10**：加权和仍是 0–100，开根号后乘 10 把分数整体抬到 0–100 的同一区间——单调变换，**相对排名不变**，但中低分不再挤在低位（原始 35 分 → 59.2，原始 100 分 → 100）；
- 最后按约束封顶：**硬约束未满足 ≤ 20 分，软约束未满足 ≤ 60 分**（第一页 `priority: "must" | "should"`，缺省按硬约束处理）；被封顶的方案在排名里标「硬/软约束封顶」，首选卡里同时显示封顶值和原始分；
- 权重自动归一化：合计不是 100% 也照常算，`0%` 表示该维度不参与评分；
- 五个场景预设（权重顺序：成本 / 重量 / 性能 / 风险 / 约束）：均衡 20/20/20/25/15、成本优先 40/10/10/20/20、轻量优先 15/40/10/20/15、**安全优先 15/10/5/55/15**、**性能优先 10/10/55/10/15**；拖动任意滑杆即切换为「自定义」（滑杆上限 60%）；
- 风险维度内部固定 60% / 40%：零件风险等级为主，交期只占四成——交期不再单独占一个权重，但仍然完整地影响评分与「安全优先」预设；
- 展示：首选方案卡（得分 + 领先分差 + 优势维度）、排名列表（每行一根 **0–100 线性条，100 占满、0 为空**，颜色 = 各维度贡献）、底部权重图例；权重存在 `sessionStorage`，刷新不丢（旧版五项权重的会话会自动作废，回到「均衡」）；
- 全部权重归零时显示「至少保留一项权重，才能生成评分」，不做除零处理；
- 评分只在「开始对比」之后、且至少两列（系统推荐 + 1 个用户方案）时出现，删光用户方案后自动隐藏。

对应实现：`public/next.js` 的 `SCORE_DIMS` / `SCORE_PRESETS` / `weightedScore()` / `renderScore()` / `paintScore()`，样式在 `public/next.css` 的 `.s2-score` 段。

### 交付排期：甘特图 + 流程图

第二个页签（`#view-delivery`）把原来占位的「周期风险」和「人员协作」并成一屏：**上半屏甘特图管时间，下半屏流程图管依赖，两张图同源**（都由 `dlvPlan()` 算出来，不存在各画各的）。

**取数与排期规则**

- 排期基准默认是当前**得分最高**的完整方案（系统推荐或某个用户方案，下拉可切），取它每个零件的 `leadTime`；
- 28 个零件按 7 个模块分组成 **7 组采购**，到料日 = 组内最晚那个零件的交期；
- 之后是 **2 道组装 + 1 道检查**：轴系与手柄结构组装（等俯仰 / 横滚 / 航向 / 手柄 4 组齐套）、电气总装与整机集成（等轴系装完 + 相机 / 控制 / 电源 3 组到料）、整机检查与验收（总装下线后）；
- **AI 3 条任务**：到料风险预测与齐套预警（贯穿采购）、装配序列与工位排程（轴系开工前 2 天）、视觉检测与验收报告（与检查并行）；
- 合计 **13 项任务** = AI 3 + 非 AI 10（采购 7 + 组装 2 + 检查 1），人物 3 人（周予 / 陈屿 / 苏航）+ AI。

**资源调平（同一人绝不重叠，总时长不变）**

- 采购条只画"人真正干活的那半天"（下单），供应商交期画成浅色虚线轨道 + 到料菱形 —— 交期是人等出来的，不占人；
- 7 张采购单按**半天一个工位**铺开：**同一时刻周予手上只有一单**，绝不重叠；一天最多两单（上午一单下午一单）；
- 铺单顺序由"最晚下单日"决定（= 该组所在工序最晚开工日 − 交期），最紧的 4 单（电源 43 天 + 三个 39 天）必须压在前两天内下完，其余 3 单按各自的富余量往后铺（演示里落在 D4 / D7 / D11），并让开已经占用的到料日；
- **总时长不变**：调平后再算一遍总时长，如果比"全部第 0 天下单"还长就自动退回原方案（`dlvPlan()` 里有这条兜底）；
- 结果（演示数据）：同一人重叠 **0 处** · 同日开工最多 **2 项** · 同日收尾最多 **1 项** · 总时长仍是 **48 天** —— 这三项在页面「人员协作」卡底部实时显示，也写在 `__STAGE2_DELIVERY__().stats` 里。

**用户只填两个日期**

- 起始日期、终止日期决定窗口天数；条形位置不动（那是交期算出来的），变的是刻度、月份条、周末底纹、余量和超窗提示；
- 窗口比计划短：多出来的任务条压到窗口右端并打上红色斜纹 + 「超窗」标签，顶部给出一句提示，可点「按交期自动排」把窗口拉到 `need` 天；
- 窗口比计划长：尾部留出缓冲，预警线写「计划完成 · 余量 N 天」；
- 默认起始日是「下一个周一」，终止日按计划天数自动补齐；日期窗与排期基准存 `sessionStorage`，刷新/重进还原。

建议用独立实例 + 临时数据目录跑验收，避免污染真实 `data/`：

```powershell
# PowerShell
$env:PORT="43126"; $env:ATLAS_DATA_DIR="C:\tmp\atlas-e2e"; $env:AI_MOCK="1"; node server.mjs
cd ../../requirement-intake-v2-checks; $env:APP_URL="http://127.0.0.1:43126/"; node scripts/browser-check.mjs
```

联网链路可以在没有真实 Key 的情况下验收 —— `scripts/stub-ai.mjs` 是一个本地 OpenAI 兼容假服务，返回带 `【STUB】` 前缀的合法函数调用，用来证明请求确实走了 HTTP：

```bash
node scripts/stub-ai.mjs                        # http://127.0.0.1:43199/v1
AI_CONFIG_FILE=/tmp/live.env APP_URL=http://127.0.0.1:43127/ node scripts/live-check.mjs
```

`live-check` 只改 `AI_CONFIG_FILE` 指向的临时配置（默认 `ai-config.env`），结束时自动还原；会断言：徽标变成「来源 · 模型」、`/api/config` 不含 Key、回复来自 stub、表1 链接可打开、非法端点显示配置错误、还原后回到 MOCK。

第二页的推荐与评分可以在页面里直接自检（打开 `next.html?demo=1`，控制台执行）：

```js
__STAGE2_REC__()             // 极速引擎快照：算法、五路起点的起止分/步数/试算量、每步置换、基线/推荐得分
__STAGE2_SOLVER_CHECK__(3)   // 裁剪到前 3 个零件类型（1,000 种组合），枚举 / 单起点 / 多起点各跑一遍并比较得分
__STAGE2_DELIVERY__()        // 交付排期快照：排期基准、日期窗与余量、13 项任务的起止天、7 组交期、预警线
```

`__STAGE2_SOLVER_CHECK__` 的输出形如：`{ combos: 1000, enumScore: 84.33, greedyScore: 75.89, multiScore: 84.33, multiBetter: true, exactBetter: false }`——多起点在这一档追平了精确枚举，单起点差 8.4 分。

`?rec=enum` 会尝试走精确枚举；组合数超过 `REC_ENUM_LIMIT`（20 万）时自动回退极速引擎，并在引擎条上写明"已回退"。
